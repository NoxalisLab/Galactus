# Continuous integration

Two workflows. One runs on every change and gates it. One is triggered by hand
or by a tag and produces the artifact.

## `.github/workflows/ci.yml`

Runs on every push to any branch and on every pull request. Three jobs, in
parallel, all on `macos-15`, which is Apple Silicon.

| Job | What it runs | Gate |
| --- | --- | --- |
| `invariants` | `python3 scripts/check-dashes.py`, `python3 scripts/check-skills.py` | blocking |
| `frontend` | `npm ci`, `npm run tslib`, `npx tsc --noEmit`, `npm test` | blocking |
| `rust` | `cargo fetch --locked`, `cargo test --offline` | blocking |
| `rust` | `cargo clippy --offline --all-targets`, `cargo fmt --all -- --check` | advisory |

At the time of writing that is 822 TypeScript tests across 16 suites and 177
Rust tests.

### Why macOS on Apple Silicon, asserted rather than assumed

Every job starts by checking `uname -s` and `uname -m` and fails if either is
wrong. The label `macos-15` means arm64 today; a silent change of that meaning
would otherwise turn a green run into a lie. The Rust side links against macOS
frameworks through Tauri, the pty suite opens a real pseudo terminal, and the
product only ever ships as an arm64 bundle, so a pass anywhere else would prove
nothing.

### Why `npm run tslib` is a step

`app/public/tslib` is generated by `tools/tsintel/copy-libs.mjs` and is not
committed, on purpose: committing it would make the repository diverge from the
installed TypeScript version. Three tsintel suites read it. Locally it is
already on disk because `npm run build` regenerates it; in CI, where every
checkout is clean, it has to be created explicitly or `npm test` fails.

### Why `cargo fetch --locked` and then `cargo test --offline`

`--offline` is the semantics the project wants for the compile: no network, no
resolution, exactly the pinned dependency set. A clean runner has an empty
cargo cache, so a bare `cargo test --offline` fails on the first missing crate.
The download is therefore one explicit step, with `--locked` so it cannot touch
`Cargo.lock`, and everything after it is offline.

This is not hypothetical. The same failure reproduces locally on the
development machine whenever a crate is missing from the cache:

```
error: failed to download `atomic-waker v1.1.2`
Caused by: attempting to make an HTTP request, but --offline was specified
```

### Caching

npm is cached by `actions/setup-node` keyed on `app/package-lock.json`.

Cargo is cached with `actions/cache` over the registry index, the registry
cache, the git database and `app/src-tauri/target`, keyed on `Cargo.lock`
alone. Keying on the sources as well would throw the cache away on every commit,
and the expensive half of a cold build is the dependency tree, which changes
only when the lockfile does. `actions/cache` writes a new entry only on a key
miss, so the entry refreshes exactly when the dependency set changes.
`CARGO_INCREMENTAL=0` keeps the cached directory from filling with incremental
artifacts that are never reused across runners.

Only first party actions are used: `actions/checkout`, `actions/setup-node`,
`actions/cache`, `actions/upload-artifact`. The release attachment is done with
the preinstalled `gh` CLI rather than a third party release action.

### Clippy and rustfmt are advisory, on purpose

They are wired up, they run, and their output is visible, but they do not fail
the build yet, because the tree is not clean under either of them:

- `cargo clippy --all-targets` produces 21 warnings across the lib and its
  tests. All are style level: `manual_range_contains`, `useless_format`,
  `lines_filter_map_ok`, dead test helpers, and similar.
- `cargo fmt --all -- --check` wants 342 hunks across 22 files.

Reformatting 22 files to turn a check green would bury every other change in
the diff for weeks. When someone lands that reformat deliberately, promoting
both to gates is a two line change: drop `continue-on-error` and add
`-- -D warnings` to the clippy invocation.

### Node version

Pinned to `24`. Node 21 or newer is required, because the suites are driven by
`node --test` with glob patterns. Bumping it is one line.

## `.github/workflows/release-dmg.yml`

Triggered by `workflow_dispatch` or by pushing an `app-v*` tag. Builds, signs,
notarizes, staples, verifies, uploads the dmg as a workflow artifact, and
attaches it to the GitHub release.

**It does not run on a GitHub hosted runner.** Two reasons, neither temporary:

1. The patched llama.cpp engine lives under `third_party/`, which is git
   ignored. A hosted runner would have to clone upstream at the pinned commit,
   apply five patches and run a full Metal build before it could start.
2. The Developer ID private key belongs in one keychain on one machine, not in
   an ephemeral VM as a base64 secret.

So the build machine is registered as a self hosted runner. The workflow starts
with a preflight that fails immediately, with a specific message, if the engine
path, Homebrew OpenSSL, `swiftc`, `gh` or the signing identity is missing, so a
misconfigured runner costs a second rather than an hour.

Configuration and credentials are documented in
[RELEASE-SIGNING.md](RELEASE-SIGNING.md). Nothing credential shaped is stored
in this repository.

## What has not been verified

These workflows have never executed. Nothing here can run GitHub Actions. What
was checked, on the development machine:

- `actionlint` 1.7.12 reports zero problems on both files, which covers the
  schema, the expression syntax, the runner labels, the action versions and
  shellcheck over every inline `run` block.
- every command the CI workflow runs was executed by hand and passed:
  `check-dashes.py` at zero, `check-skills.py` clean, `npx tsc --noEmit` clean,
  `npm test` at 822 passed and 0 failed, `cargo test --offline` at 177 passed
  and 0 failed.
- `shellcheck` is clean at warning level on every script.

What was not checked, and cannot be from here: whether the caches actually
restore, whether `macos-15` is provisioned for this account, whether `npm ci`
resolves identically on a clean runner, and every step of the release workflow,
which needs a self hosted runner and a Developer ID certificate.
